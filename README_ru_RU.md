# biangbiang

[简体中文](README.md) · [繁體中文](README_zh_TW.md) · [English](README_en_US.md) · [Polski](README_pl_PL.md) · **Русский** · [Svenska](README_sv_SE.md)

![100% SLOP — но этот значок нарисован вручную](.github/assets/slop_badge.webp)

Самостоятельно размещаемое **зеркало артефактов релизов GitHub**. Оно следит за последним релизом каждого проекта из `config.xml`, скачивает его артефакты на ваш сервер и раздаёт их через быстрый, адаптированный под мобильные устройства фронтенд на Vue + [Ant Design Vue](https://antdv.com).

Весь проект работает в **одном контейнере Docker**: единственный процесс Node.js (Express) отдаёт API, зеркалированные файлы и собранное одностраничное приложение.

> Адрес репозитория: <https://github.com/xiaomianguan/biangbiang/>
> Документация по развёртыванию: [Руководство по развёртыванию (русский)](ADVANCED_INSTRUCTION_ru_RU.md) · [Advanced Deployment Guide (English)](ADVANCED_INSTRUCTION_en_US.md)

## Возможности

- **Работает сразу**: в репозитории уже есть готовые `config.xml`, `overwrite.xml` и `assets/` (favicon, иконки проектов и прилагаемый шрифт). Склонируйте его и выполните `docker compose up -d --build` — вы сразу увидите полноценный сайт, ничего подготавливать не нужно. Можно развивать этот пример или удалить его и начать с нуля.
- **Автоматическое зеркалирование** всех артефактов, приложенных к релизу GitHub.
- **Архивы исходников исключены** — архивы `Source code (zip)` / `Source code (tar.gz)`, которые GitHub добавляет автоматически, никогда не зеркалируются.
- **Проверка обновлений каждые 24 часа** (настраивается), при этом на диске хранится только последняя версия каждого проекта.
- **Любое количество проектов** — один `<project>` в `config.xml` соответствует одной карточке.
- **Ручные записи** — если записать `<repo>overwrite@{number}</repo>`, данные карточки берутся из `overwrite.xml`, поэтому проекты с GitHub и произвольные внешние ссылки на скачивание могут соседствовать на одном сайте.
- **Полностью настраивается конфигурацией**: заголовок, favicon и иконка/название/репозиторий каждого проекта берутся из `config.xml`; иконки — это обычные файлы PNG/WEBP, а в репозитории есть готовый пример, который можно свободно заменить.
- **Необязательная сортировка карточек**: задайте `<sortable>true</sortable>`, и в шапке появится список сортировки, позволяющий посетителям упорядочить карточки по алфавиту, времени обновления, наибольшему или наименьшему числу файлов. Значение `false` (или отсутствие тега) сохраняет точный порядок записей из `config.xml`.
- **Настраиваемый акцентный цвет**: укажите в `<accent>` название цвета из [базовых палитр](https://ant.design/docs/spec/colors) Ant Design (например, `volcano` или `purple`), и сайт использует его вместо фирменного синего. Если тег отсутствует или написан с ошибкой, остаётся синий по умолчанию.
- **Настраиваемый шрифт**: укажите в `<font>` путь к файлу шрифта (например, `.woff2`), и весь сайт — включая компоненты Ant Design — переключится на него. Путь разрешается относительно `config.xml`, так же как `<favicon>`. Если тег отсутствует или файла нет, остаётся системный шрифт.
- **Светлая и тёмная темы**, по умолчанию «как в системе», с возможностью принудительного выбора. Реализовано на токенах дизайна Ant Design Vue.
- **Устанавливается как PWA** (manifest + Service Worker) — по замыслу **без офлайн-кэширования**; имя приложения следует за `<title>`, а иконки — за `<favicon>`.
- **Многоязычный интерфейс**: задайте `<lang>` как `zh_cn`, `zh_tw`, `en_us`, `pl_pl`, `ru_ru` или `sv_se`, и весь интерфейс — тексты, форматы дат и подписи, которые Ant Design отрисовывает внутри своих компонентов, — переключится на этот язык. Если тег отсутствует или значение неизвестно, остаётся упрощённый китайский.
- **Адаптивная сетка карточек** — одна колонка на телефоне, две на планшете, три на компьютере. Каждая карточка подстраивается под собственное содержимое и не растягивается до самой высокой в ряду. Низкая карточка к тому же всплывает в свободное место под собой, поэтому отступ между карточками всегда равен 16 px: Safari 26.4+ делает это нативно благодаря Grid Lanes, а в остальных браузерах карточки раскладывает сам фронтенд.
- **Устойчивость к ошибкам**: один сломанный или неверно указанный репозиторий не роняет весь сайт — проект, синхронизация которого не удалась, сохраняет последние успешные данные. Пример конфигурации намеренно оставляет две неработающие карточки, чтобы это продемонстрировать.

## Как это работает

```text
                    каждые 24 ч  ┌──────────────────────────────┐
        GitHub REST API ───────► │  Движок зеркала (бэкенд)     │
   (releases/latest)             │  · получить последний релиз  │
                                 │  · скачать артефакты         │
                                 │  · удалить старые версии     │
                                 └──────────────┬───────────────┘
                                                │ запись
                                                ▼
                              data/releases/{owner}/{repo}/{version}/{file}
                                                │
   браузер ──► Express ─────────────────────────┘
                 ├─ /                  → собранное приложение Vue (статика)
                 ├─ /api/state         → текущий JSON: заголовок, проекты, версии
                 ├─ /media/{path}      → favicon и иконки проектов из каталога конфигурации
                 └─ /dl/{owner}/{repo}/{version}/{file}  → зеркалированные артефакты
```

Фронтенд — это **статическая сборка**, но данные для отображения он получает во время работы через `GET /api/state`. Когда выходит новый релиз и попадает в зеркало, метки версий и набор кнопок скачивания обновляются сами — **пересобирать фронтенд не нужно никогда**. Страница также периодически обновляет данные (и делает это, когда вкладка снова получает фокус), поэтому давно открытые страницы остаются актуальными.

## Конфигурация (`config.xml`)

`config.xml` лежит рядом с каталогом `assets/`. Все пути к изображениям разрешаются **относительно каталога, в котором находится `config.xml`**, поэтому иконки могут лежать как рядом с ним, так и в подкаталоге `assets/`.

```xml
<favicon>assets/favicon.png</favicon>
<title>Page title</title>
<lang>zh_cn</lang>
<sortable>true</sortable>
<accent>volcano</accent>
<font>assets/MyFont.woff2</font>

<project>
    <icon>assets/icon1.png</icon>
    <name>Project 1</name>
    <repo>https://github.com/user/project1</repo>
</project>

<project>
    <icon>assets/icon2.webp</icon>
    <name>Project 2</name>
    <repo>https://github.com/user/project2</repo>
</project>
```

| Тег          | Расположение  | Описание |
|--------------|---------------|----------|
| `<title>`    | корень        | Заголовок сайта: показывается в шапке, на вкладке браузера и как **имя установленного приложения** (записывается в manifest при каждом запуске). |
| `<lang>`     | корень        | Необязательный. Язык интерфейса: `zh_cn`, `zh_tw`, `en_us`, `pl_pl`, `ru_ru` или `sv_se` (регистр не важен; дефис тоже принимается, поэтому `zh-CN` работает). Отсутствующий, пустой или неизвестный тег даёт `zh_cn` (упрощённый китайский). |
| `<favicon>`  | корень        | Необязательный. Файл PNG/WEBP, используемый как favicon сайта. |
| `<sortable>` | корень        | Необязательный. Значение `true` добавляет в шапку список сортировки, позволяя посетителям упорядочить карточки по алфавиту, времени обновления, наибольшему или наименьшему числу файлов — по умолчанию по алфавиту. Значение `false` (или отсутствие тега) сохраняет точный порядок записей `<project>`. |
| `<accent>`   | корень        | Необязательный. Название базовой палитры Ant Design — `red`, `volcano`, `orange`, `gold`, `yellow`, `lime`, `green`, `cyan`, `blue`, `geekblue`, `purple` или `magenta` (регистр не важен). Заменяет фирменный синий (Daybreak Blue). Отсутствующее, пустое или неизвестное значение даёт синий по умолчанию. |
| `<font>`     | корень        | Необязательный. Путь к файлу шрифта (например, `assets/MyFont.woff2`), разрешается относительно `config.xml` точно так же, как `<favicon>`. Весь сайт — включая компоненты Ant Design — переключается на этот шрифт. Отсутствующий, пустой или несуществующий файл оставляет системный шрифт. |
| `<project>`  | корень (0..N) | Одна запись на проект → одна карточка на сайте. |
| `<icon>`     | в проекте     | Файл PNG/WEBP, используемый как иконка карточки. Необязательный. |
| `<name>`     | в проекте     | Отображаемое название проекта. |
| `<repo>`     | в проекте     | Адрес репозитория GitHub. |

**Поддерживаемые формы `<repo>`** (все разрешаются в `owner/repo`):

```text
https://github.com/user/project1
https://github.com/user/project1.git
https://github.com/user/project1/
git@github.com:user/project1.git
user/project1
```

Количество записей `<project>` можно менять свободно — сайт отрисовывает ровно одну карточку на каждую корректную запись. Записи с отсутствующим или неверным `<repo>` пропускаются и не влияют на остальные.


### Ручные записи (`overwrite.xml`)

`<repo>` не обязательно должен указывать на GitHub. Запись `overwrite@{number}` означает, что данные этой карточки берутся из файла `overwrite.xml`, лежащего **рядом** с `config.xml`:

```xml
<project>
    <icon>assets/icon2.webp</icon>
    <name>Мой приватный проект</name>
    <repo>overwrite@1</repo>
</project>
```

Структура `overwrite.xml`:

```xml
<overwrite>
    <id>1</id>
    <version>1.0.0</version>
    <repo>https://example.com/my-project</repo>
    <downloads>
        <file>https://example.com/artifact.zip</file>
        <file>https://example.com/artifact2.rar</file>
    </downloads>
</overwrite>
```

| Тег                  | Описание |
|----------------------|----------|
| `<id>`               | Соответствует числу в `overwrite@{number}` из `config.xml`. |
| `<version>`          | Версия, показываемая на карточке вместо полученной автоматически. Необязательный. |
| `<repo>`             | Адрес, на который ведёт кнопка «Открыть репозиторий». Необязательный: без него кнопка не показывается. |
| `<downloads>/<file>` | Каждый `<file>` — отдельная кнопка скачивания, ведущая прямо по указанной ссылке. |

Что полезно знать:

- `overwrite.xml` читается **только** тогда, когда в `config.xml` есть хотя бы одна запись `overwrite@{number}`. Если все `<repo>` — адреса GitHub, файл вообще не открывается.
- Ручные записи **ничего не скачивают и не кэшируют** — кнопки ведут прямо по указанным адресам, поэтому они не занимают место на диске и не подпадают под лимиты API GitHub.
- Ручные записи **не показывают дату публикации** (релиза нет, значит нет и даты) и размер файла (он неизвестен).
- Проекты с GitHub и ручные записи можно свободно смешивать в одном `config.xml`.
- Имя файла на кнопке скачивания — последний сегмент ссылки.
- При развёртывании в Docker `overwrite.xml` монтируется только для чтения рядом с `config.xml`, поэтому ничего дополнительно настраивать не нужно.

> **В репозитории есть готовый набор примеров.** В свежесклонированном репозитории уже лежат `config.xml`, `overwrite.xml` и `assets/` (favicon, иконки проектов и прилагаемый шрифт), поэтому `docker compose up -d --build` даёт полноценный сайт без единой правки. Чтобы придать ему свой вид, замените файлы в `assets/` и укажите их в конфигурации; чтобы начать с нуля, удалите примеры и оставьте только свою конфигурацию.

## Быстрый старт (Docker)

> **Разворачиваете на публичном сервере?** Смотрите руководства по развёртыванию:
> [русский](ADVANCED_INSTRUCTION_ru_RU.md) ·
> [English](ADVANCED_INSTRUCTION_en_US.md).
> В них описаны пример `docker-compose.advanced.yml`, подробный разбор `config.xml`,
> размещение изображений и публикация контейнера через nginx с HTTPS.

### 1. Получите проект

Склонируйте репозиторий и переключитесь на **последний стабильный релиз** (самый свежий тег релиза):

```bash
git clone https://github.com/xiaomianguan/biangbiang.git
cd biangbiang
git checkout "$(git tag --sort=-v:refname | head -1)"   # самый свежий тег релиза
```

> **Нужна версия для разработки (ветка `main`)?** Пропустите последнюю строку `git checkout` — вы останетесь на `main`. В ней самые свежие изменения, но они ещё не выпущены и могут быть нестабильны.

### 2. Подготовьте конфигурацию и иконки (необязательно — в репозитории есть рабочий пример)

```
biangbiang/
├── config.xml
├── overwrite.xml           # ручные записи: нужны только для overwrite@{number}
└── assets/
    ├── favicon.png
    ├── icon1.png
    └── icon2.webp
```

В свежесклонированном репозитории **уже есть** всё перечисленное, поэтому этот шаг необязателен: `docker compose up -d --build` сразу даёт полноценный сайт. Чтобы сделать его своим, отредактируйте `config.xml`, указав заголовок и свои проекты (синтаксис — в предыдущем разделе), и замените изображения в `assets/`.

> **В примере конфигурации две намеренно неработающие карточки.** В прилагаемом `config.xml` используются `https://github.com/user/project2` (несуществующий репозиторий) и `overwrite@2` (нет подходящего `<id>` в `overwrite.xml`), чтобы показать оба состояния ошибки — они демонстрируют, как ведёт себя сайт, когда репозиторий указан с ошибкой или отсутствует ручная запись. Это задумано, а не баг. Удалите их или укажите свои проекты.

> **Используете ручные записи?** Просто заполните их в `overwrite.xml` — `docker-compose.yml` уже монтирует этот файл в контейнер.
>
> После правки файла на хосте нажмите «Проверить обновления» в интерфейсе — пересобирать контейнер не нужно.
>
> Следите, чтобы файл существовал: если `./overwrite.xml` пропадёт, Docker создаст на его месте пустой каталог, и связанные карточки будут падать с ошибкой `EISDIR`. В репозитории есть готовый пример, так что это касается только тех, кто его удалил.

### 3. Соберите и запустите

```bash
docker compose up -d --build
```

### 4. Откройте сайт

Перейдите в браузере на <http://localhost:8080>.

Первая синхронизация стартует сразу при запуске контейнера; далее она выполняется каждые 24 часа (см. `CHECK_INTERVAL_HOURS`). Зеркалированные артефакты сохраняются в каталоге `./data` на хосте и переживают перезапуск.


### Без Compose

```bash
docker build -t biangbiang .
docker run -d --name biangbiang -p 8080:8080 \
  -v "$PWD/config.xml:/app/config.xml:ro" \
  -v "$PWD/assets:/app/assets:ro" \
  -v "$PWD/data:/app/data" \
  biangbiang
```

### Полезные команды

```bash
docker compose logs -f          # следить за логами
docker compose restart          # перезапуск (заново создаёт иконки PWA и имя приложения)
docker compose down             # остановить и удалить контейнер
```

### Обновление до последней версии

Стабильные релизы публикуются как теги. Загрузите теги, переключитесь на самый свежий из них и пересоберите контейнер:

```bash
git fetch --tags
git checkout "$(git tag --sort=-v:refname | head -1)"   # самый свежий тег релиза
docker compose up -d --build
```

> Переключение на тег оставляет вас в состоянии detached HEAD, что для развёртывания не имеет значения. Чтобы закрепить конкретную версию, замените `"$(...)"` на имя тега, например `v1.0.2`.

В версии для разработки (ветка `main`) по-прежнему нужен `git pull`:

```bash
git pull
docker compose up -d --build
```

`./config.xml`, `./overwrite.xml`, `./assets` и `./data` сохраняются на хосте через монтирование, поэтому обновления их не затрагивают.

## HTTP-интерфейс

| Метод  | Путь                                  | Описание |
|--------|---------------------------------------|----------|
| `GET`  | `/api/state`                          | Текущее состояние сайта: заголовок, favicon, проекты, версии и артефакты. |
| `GET`  | `/api/health`                         | Проверка работоспособности (проба живости). |
| `POST` | `/api/refresh`                        | Немедленно запускает зеркалирование (используется кнопкой «Проверить обновления»). |
| `GET`  | `/media/{path}`                       | Favicon и иконки проектов, разрешаются относительно каталога конфигурации. |
| `GET`  | `/dl/{owner}/{repo}/{version}/{file}` | Скачать зеркалированный артефакт. |

> Фрагменты `{...}` выше — это подстановки; в реальном запросе подставьте конкретные значения (например, вместо `{owner}` — владельца репозитория). Во всей этой документации `<...>` обозначает только XML-теги.

Пример ответа `GET /api/state`:

```json
{
  "title": "Page title",
  "lang": "zh_cn",
  "favicon": "/media/assets/favicon.png",
  "lastUpdated": "2026-01-01T12:00:00.000Z",
  "projects": [
    {
      "id": "user/project1",
      "name": "Project 1",
      "icon": "/media/assets/icon1.png",
      "repo": "https://github.com/user/project1",
      "version": "v2.4.0",
      "status": "ok",
      "assets": [
        { "name": "project1-linux-amd64.tar.gz", "size": 1234567,
          "url": "/dl/user/project1/v2.4.0/project1-linux-amd64.tar.gz" }
      ]
    }
  ]
}
```

`status` принимает значения `ok`, `empty` (релиза пока нет) или `error` (например, репозиторий не существует). Проект, синхронизация которого не удалась, сохраняет последние успешно зеркалированные данные.

## Заметки

### Тема
По умолчанию тема работает в режиме **«как в системе» (auto)**, следуя светлым или тёмным настройкам системы и обновляясь на лету. Переключатель в шапке позволяет принудительно выбрать **светлую** или **тёмную** тему; выбор сохраняется в `localStorage`. Обе темы используют токены `defaultAlgorithm` / `darkAlgorithm` Ant Design Vue.

### PWA
Приложение поставляется с `manifest.webmanifest` и минимальным Service Worker, поэтому его можно установить на главный экран или рабочий стол. Service Worker **ничего не кэширует** — это чистый сетевой проброс, поэтому офлайн-режима нет по замыслу.

**Иконки установленного приложения всегда следуют за `<favicon>`**, а **имя приложения — за `<title>`**. При каждом запуске бэкенд строит из favicon полный набор иконок с помощью ImageMagick:

| Результат | Размер | Описание |
|-----------|--------|----------|
| `pwa-192x192.png` | 192×192 | Прозрачность сохранена, дополнено до квадрата |
| `pwa-512x512.png` | 512×512 | Прозрачность сохранена, дополнено до квадрата |
| `pwa-maskable-512x512.png` | 512×512 | Логотип масштабирован до 80%, фон залит средним цветом favicon |
| `apple-touch-icon.png` | 180×180 | Сплющено на белом фоне (iOS не поддерживает прозрачность) |

Иконки записываются в `{DATA_DIR}/pwa/` и отдаются по путям, объявленным в manifest. При каждом запуске бэкенд также заново создаёт в том же каталоге файл `manifest.webmanifest`, подставляя в его `name` / `short_name` (имя, под которым приложение установлено) значение `<title>` из `config.xml` и записывая в `lang` тег BCP-47, соответствующий `<lang>`; остальные поля (описание, цвета, список иконок) берутся из шаблона, входящего в сборку фронтенда. Поэтому достаточно изменить `<favicon>`, `<title>` или `<lang>` и перезапустить контейнер, чтобы обновить иконки, имя и язык приложения. Favicon может быть в любом формате, который читает ImageMagick (PNG, WEBP и т. д.). Если `<favicon>` не задан или ImageMagick недоступен, используются стандартные иконки из `frontend/public/`; если шаблон manifest прочитать не удалось, используется стандартный manifest.

ImageMagick уже установлен в образе Docker. Для локальной разработки установите его самостоятельно (`brew install imagemagick`, `apt install imagemagick` и т. д.).

### Лимиты API
Неавторизованные запросы к API GitHub ограничены 60 в час, что с запасом хватает для нескольких проектов при одной проверке в сутки. Если проектов много, задайте `GITHUB_TOKEN` в `docker-compose.yml`.

### Работа без прав root
Entrypoint контейнера запускается от root, передаёт каталог `./data` пользователю `node` (uid 1000) и сразу сбрасывает права — поэтому смонтированный каталог работает сразу и вручную вызывать `chown` не нужно. Если вы принудительно задали другого пользователя через `user:` или `--user`, у него должен быть доступ на запись в `./data`.
