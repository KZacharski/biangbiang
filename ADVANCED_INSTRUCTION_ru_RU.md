# biangbiang — Руководство по развёртыванию (Docker + nginx + HTTPS)

## 1. Итоговая архитектура

```
        Интернет
            │  https://mirror.example.com
            ▼
    ┌───────────────────┐
    │  nginx (хост)     │  завершение TLS, прослушивание 443
    │  Let's Encrypt    │
    └─────────┬─────────┘
              │  proxy_pass http://127.0.0.1:8080
              ▼
    ┌───────────────────┐
    │  biangbiang       │  единственный контейнер Docker
    │  Express + SPA    │  (не выставлен напрямую в интернет)
    └─────────┬─────────┘
              │  каждые 24 часа
              ▼
        GitHub REST API  →  ./data/releases/{owner}/{repo}/{version}/{file}
```

Один контейнер отдаёт API, зеркалированные артефакты **и** собранное одностраничное приложение Vue. Данные и артефакты лежат в bind mount (`./data`), поэтому `docker compose up --build` ничего не теряет.

## 2. Требования

| Компонент | Описание |
|---|---|
| Сервер Linux | Любой дистрибутив с поддержкой Docker. Для старта достаточно 1 ядра и 1 ГБ памяти. |
| Docker Engine | Версия 24 или новее с плагином Compose v2 (команда `docker compose`, а не `docker-compose`). |
| Место на диске | Планируйте исходя из размера артефактов. biangbiang **хранит только последнюю версию каждого проекта**, поэтому объём предсказуем. |
| Домен | Например, `mirror.example.com`, с возможностью менять его DNS-записи. |
| nginx | Установлен на хосте (`apt install nginx`) — это руководство исходит из nginx на хосте. |
| certbot | Для получения бесплатного сертификата Let's Encrypt. |

> Самому контейнеру **не нужны** никакие инструменты с хоста: Node 22, ImageMagick и все зависимости уже в образе.

## Шаг 1 — разместите код на сервере

Склонируйте репозиторий и переключитесь на **последний стабильный релиз** (самый свежий тег релиза):

```bash
sudo mkdir -p /srv/biangbiang
sudo chown "$USER":"$USER" /srv/biangbiang
cd /srv/biangbiang
git clone https://github.com/xiaomianguan/biangbiang.git .
git checkout "$(git tag --sort=-v:refname | head -1)"   # самый свежий тег релиза
```

> **Нужна версия для разработки (ветка `main`)?** Пропустите последнюю строку `git checkout` — вы останетесь на `main`. В ней самые свежие изменения, но они ещё не выпущены и могут быть нестабильны.

> **Шаг `chown` пропускать нельзя.** Каталог, созданный через `sudo mkdir`, принадлежит `root`, и всё, что появится внутри (включая `./data`), наследует этого владельца. Контейнер работает от непривилегированного пользователя, поэтому `./data` с владельцем `root` приведёт к `EACCES` при первой же записи.

Если у сервера нет доступа к GitHub, соберите образ локально и отправьте его в реестр, а в файле Compose замените `build:` на `image:`.

Теперь подготовьте структуру каталогов для развёртывания:

```bash
cp docker-compose.advanced.yml docker-compose.yml
cp .env.example .env
mkdir -p data            # config.xml, overwrite.xml и assets/ уже в репозитории; нужен только data/
```

> В `./data` пишет контейнер. При старте он сам исправляет владельца (см. [Владелец файлов](#владелец-файлов)), поэтому вручную вызывать `chown` не нужно.

С этого момента важны только четыре пути:

| Путь | Назначение |
|---|---|
| `config.xml` | Конфигурация сайта (монтируется в контейнер только для чтения). |
| `overwrite.xml` | Ручные записи (проекты вне GitHub), монтируется только для чтения. Читается только тогда, когда `config.xml` использует `overwrite@{number}`. |
| `assets/` | Ваш favicon и иконки проектов (монтируется только для чтения). |
| `data/` | Артефакты, `state.json`, сгенерированные иконки PWA и manifest. **Обязательно делайте резервные копии.** |

## Шаг 2 — напишите config.xml

`config.xml` — **единственный** файл, определяющий, что показывает сайт. Контейнер читает его из `/app/config.xml` и разбирает заново при каждой синхронизации, поэтому после правки конфигурации достаточно перезапустить контейнер — пересобирать образ не нужно.

В репозитории **уже есть готовый `config.xml`**, а вместе с ним `overwrite.xml` и `assets/`, так что этот шаг тоже можно пропустить — развёртывание «как есть» даёт полноценный сайт. «Минимальный пример» ниже показывает, как переписать его под свои проекты.

> **В примере конфигурации две намеренно неработающие карточки.** Он использует `https://github.com/user/project2` (несуществующий репозиторий) и `overwrite@2` (нет подходящего `<id>` в `overwrite.xml`), чтобы показать оба состояния ошибки — они демонстрируют поведение сайта при неверно указанном репозитории или отсутствующей ручной записи. Это задумано, а не баг. Удалите их или укажите свои проекты.

### Минимальный пример

```xml
<favicon>assets/favicon.png</favicon>
<title>Моё зеркало</title>
<lang>zh_cn</lang>
<sortable>true</sortable>
<accent>volcano</accent>
<font>assets/MyFont.woff2</font>

<project>
    <icon>assets/icon1.png</icon>
    <name>Project 1</name>
    <repo>https://github.com/user/project1</repo>
</project>

<project>
    <icon>assets/icon2.webp</icon>
    <name>Project 2</name>
    <repo>https://github.com/user/project2</repo>
</project>
```

### Описание тегов

| Тег | Расположение | Обязателен | Поведение |
|---|---|---|---|
| `<title>` | корень | нет | Заголовок сайта в шапке, на вкладке браузера и как **имя установленного приложения**. По умолчанию `Releases`. |
| `<lang>` | корень | нет | Язык интерфейса: `zh_cn`, `zh_tw`, `en_us`, `pl_pl`, `ru_ru` или `sv_se` (регистр не важен; дефис тоже принимается, поэтому `zh-CN` работает). Переключает весь интерфейс — тексты, форматы дат и подписи, которые Ant Design отрисовывает внутри своих компонентов. Неизвестное значение даёт `zh_cn` (упрощённый китайский). |
| `<favicon>` | корень | нет | PNG/WEBP, используемый как favicon сайта **и** как источник иконок устанавливаемой PWA. По умолчанию используется встроенная иконка. |
| `<sortable>` | корень | нет | Принимает только `true` / `false` (регистр не важен). `true` добавляет в шапку список сортировки, позволяя упорядочить карточки по алфавиту, времени обновления, наибольшему или наименьшему числу файлов — по умолчанию по алфавиту. `false`, опечатка или отсутствие тега сохраняют точный порядок записей `<project>`. |
| `<accent>` | корень | нет | Название цвета из [базовых палитр](https://ant.design/docs/spec/colors) Ant Design: `red`, `volcano`, `orange`, `gold`, `yellow`, `lime`, `green`, `cyan`, `blue`, `geekblue`, `purple` или `magenta` (регистр не важен). Заменяет фирменный синий (Daybreak Blue). Отсутствующий, пустой или неизвестный тег даёт синий по умолчанию — без ошибок и без потери цветов. |
| `<font>` | корень | нет | Путь к файлу шрифта (например, `assets/MyFont.woff2`), разрешаемый **относительно каталога с `config.xml`**, точно так же, как `<favicon>`. Весь сайт — включая кнопки, теги и списки Ant Design — переключается на этот шрифт; недостающие глифы добирает системный шрифт. Отсутствующий, пустой или несуществующий файл оставляет системный шрифт. |
| `<project>` | корень (0..N) | — | Соответствует одной карточке на сайте. Количество не ограничено, карточки раскладываются в 1 / 2 / 3 колонки по ширине экрана, и каждая подстраивается под собственное содержимое — не растягивается до самой высокой в ряду. Низкая карточка дополнительно всплывает в свободное место под собой, а отступ всегда равен 16 px: Safari 26.4+ делает это нативно благодаря Grid Lanes, в остальных браузерах карточки раскладывает фронтенд. |
| `<icon>` | внутри `<project>` | нет | Миниатюра карточки (PNG/WEBP). Без неё или при ошибке загрузки карточка показывает первую букву названия проекта. |
| `<name>` | внутри `<project>` | нет | Отображаемое название. По умолчанию — название репозитория. |
| `<repo>` | внутри `<project>` | **да** | Адрес репозитория GitHub. Записи `<project>` с неверным `<repo>` молча пропускаются. |

### Поддерживаемые формы `<repo>`

Все перечисленные формы разрешаются в `owner/repo`:

```text
https://github.com/user/project1
https://github.com/user/project1.git
https://github.com/user/project1/
git@github.com:user/project1.git
user/project1
```

### Правила зеркалирования

- У каждого проекта зеркалируется **только последний релиз**; старые версии удаляются с диска.
- Зеркалируются **все артефакты**, приложенные к этому релизу.
- Архивы `Source code (zip)` / `Source code (tar.gz)`, которые генерирует GitHub, **никогда** не зеркалируются.
- Повторяющиеся записи `<repo>` автоматически отбрасываются.
- Неверный или удалённый репозиторий **не** роняет весь сайт: карточка показывает «Ошибка синхронизации» и сохраняет последние успешные данные.

### Как разрешаются пути к изображениям

Все пути к изображениям в `config.xml` разрешаются **относительно каталога, в котором лежит `config.xml`** (то есть `/app` внутри контейнера). Обе формы работают:

```xml
<icon>assets/icon1.png</icon>
<icon>icon1.png</icon>          <!-- рядом с config.xml -->
```

Поскольку `./assets` монтируется в `/app/assets` только для чтения, рекомендуем держать все изображения в `assets/`.


### Ручные записи — размещение файлов вне GitHub (overwrite.xml)

`<repo>` не обязан указывать на GitHub. Запись `overwrite@{number}` означает, что данные карточки берутся из файла `overwrite.xml` рядом с `config.xml`:

```xml
<!-- config.xml -->
<project>
    <icon>assets/icon2.webp</icon>
    <name>Мой проект</name>
    <repo>overwrite@1</repo>
</project>
```

```xml
<!-- overwrite.xml -->
<overwrite>
    <id>1</id>
    <version>1.0.0</version>
    <repo>https://example.com/my-project</repo>
    <downloads>
        <file>https://example.com/artifact.zip</file>
        <file>https://example.com/artifact2.rar</file>
    </downloads>
</overwrite>
```

| Тег | Описание |
|---|---|
| `<id>` | Соответствует числу в `overwrite@{number}`. |
| `<version>` | Версия, показываемая на карточке вместо полученной автоматически. Необязательный. |
| `<repo>` | Адрес, на который ведёт кнопка «Открыть репозиторий». Необязательный — без него кнопка не показывается. |
| `<downloads>/<file>` | Каждый `<file>` — отдельная кнопка скачивания, ведущая прямо по этой ссылке. |

Поведение:

- **Читается по необходимости.** `overwrite.xml` читается только тогда, когда в `config.xml` есть хотя бы одна запись `overwrite@{number}`; сайт из одних проектов GitHub его вообще не открывает, поэтому файл может отсутствовать.
- **Ничего не скачивает.** Ручные записи не делают HTTP-запросов и ничего не пишут в `./data`. Кнопки ведут прямо по указанным адресам, поэтому не занимают диск и не подпадают под лимиты API GitHub.
- **Без даты публикации.** Релиза нет — значит, нет и даты; размер файла тоже неизвестен, поэтому он также не показывается.
- **Свободно смешиваются.** Проекты с GitHub и ручные записи сосуществуют в любых сочетаниях.
- **Имя на кнопке** — последний сегмент ссылки (`https://cdn.example.com/x/artifact3.zip` → `artifact3.zip`).
- **Отсутствие записи не роняет сайт.** Если для `overwrite@{number}` не найдётся подходящего `<id>` или файла `overwrite.xml` нет вовсе, в состояние ошибки перейдёт только эта карточка и появится одна строка в логе; остальные проекты не пострадают.

### Монтирование overwrite.xml

`overwrite.xml` монтируется **одним файлом**, так же как `config.xml`, из `docker-compose.yml` и `docker-compose.advanced.yml`:

```yaml
      - ./config.xml:/app/config.xml:ro
      - ./overwrite.xml:/app/overwrite.xml:ro
      - ./assets:/app/assets:ro
      - ./data:/app/data
```

Файл перечитывается на каждом цикле проверки, поэтому после правки на хосте достаточно нажать «Проверить обновления» в интерфейсе или дождаться следующей проверки — **без** пересборки и без перезапуска контейнера.

> **Не удаляйте этот файл.** Если `./overwrite.xml` не существует, Docker создаст на его месте пустой **каталог**, и все карточки `overwrite@{number}` упадут с ошибкой `EISDIR`. В репозитории есть готовый пример, поэтому свежесклонированный проект этой проблемы не знает; если вы его удалили, воссоздайте через `touch /srv/biangbiang/overwrite.xml`.

## Шаг 3 — добавьте изображения

В репозитории **есть готовый набор примеров**: favicon, иконки проектов и прилагаемый шрифт в каталоге `assets/`. Вместе с примером `config.xml` свежесклонированный проект сразу даёт полноценный сайт без подготовки изображений. Ниже рассказано, как заменить их своими — по одному или удалив примеры и начав с нуля. Вид сайта полностью определяется `assets/` и `config.xml`; в самом biangbiang никаких фирменных материалов нет.

### Структура каталогов

```
/srv/biangbiang/
├── config.xml
├── assets/
│   ├── favicon.png        # favicon сайта, он же источник иконок PWA
│   ├── icon1.png          # миниатюра проекта 1
│   └── icon2.webp         # миниатюра проекта 2
└── data/
```

> Кроме `data/`, все перечисленные файлы **уже есть в репозитории**, поэтому команды `cp` ниже — это замена, а не создание; они нужны только если вы хотите собственный вид.

### 1. favicon (нужен для собственного вида)

```bash
# Положите свой логотип и укажите его в config.xml:
#   <favicon>assets/favicon.png</favicon>
cp ~/my-logo.png /srv/biangbiang/assets/favicon.png
```

- **Формат:** любой, который читает ImageMagick; PNG и WEBP проверены.
- **Размер:** рекомендуется 512×512 или больше, лучше квадрат с альфа-каналом.
- При каждом старте контейнера бэкенд выводит из этого файла весь набор устанавливаемых иконок:

  | Файл | Размер | Назначение |
  |---|---|---|
  | `pwa-192x192.png` | 192×192 | Иконка PWA, прозрачность сохранена |
  | `pwa-512x512.png` | 512×512 | Иконка PWA, прозрачность сохранена |
  | `pwa-maskable-512x512.png` | 512×512 | Адаптивная иконка Android: логотип масштабирован до 80 %, фон залит средним цветом изображения |
  | `apple-touch-icon.png` | 180×180 | Иконка на домашний экран iOS (сплющена на белом фоне) |

  Они пишутся в `data/pwa/` и отдаются бэкендом — **не** добавляйте их в репозиторий. Файл `manifest.webmanifest` в том же каталоге тоже пересоздаётся при каждом старте из `<title>`: его `name` / `short_name` — это имя, под которым устанавливается приложение, а остальные поля берутся из шаблона, входящего в сборку фронтенда.

### 2. Иконки проектов

Скопируйте по одному изображению на проект и укажите его через `<icon>`:

```bash
cp ~/project1-logo.png   /srv/biangbiang/assets/icon1.png
cp ~/project2-logo.webp  /srv/biangbiang/assets/icon2.webp
```

- Отрисовываются в размере **48×48 px** с `object-fit: cover`, поэтому лучше всего выглядят квадратные исходники.
- Тег необязателен. Без `<icon>` карточка показывает цветной квадрат с первой буквой названия проекта.

### 3. Примените изменения

Материалы смонтированы только для чтения, поэтому контейнер сразу видит новые файлы — но **иконки PWA и имя приложения создаются только при старте**:

```bash
cd /srv/biangbiang
docker compose restart biangbiang
```

> **Права.** Контейнер работает от uid/gid **1000** (`node`). Файлам в `assets/` достаточно быть доступными на чтение всем (`chmod 644` — это же и права по умолчанию при копировании). А вот `data/` должен быть **доступен на запись** для uid 1000 — см. [Текущая эксплуатация](#текущая-эксплуатация).

## Шаг 4 — запустите контейнер

Отредактируйте `.env`, созданный на шаге 1:

```ini
# Необязательно. Нужен токен с узкими правами:
# отметьте доступ только на чтение публичных репозиториев.
# Поднимает лимит API GitHub с 60 до 5000 запросов в час.
GITHUB_TOKEN=github_pat_xxxxxxxxxxxxxxxxxxxx

# Часовой пояс, в котором рендерятся отметки времени.
TZ=Asia/Shanghai
```

Затем соберите и запустите:

```bash
cd /srv/biangbiang
docker compose up -d --build
docker compose logs -f
```

В логе появится примерно следующее:

```text
[server] listening on http://0.0.0.0:8080
[server] config: /app/config.xml
[server] data:   /app/data
[server] timezone: Asia/Shanghai
[server] check interval: 24h
[pwa] generated app icons from /app/assets/favicon.png
```

### Переменные окружения

Все перечисленные переменные задаются в разделе `environment:` файла Compose.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `PORT` | `8080` | HTTP-порт внутри контейнера. |
| `HOST` | `0.0.0.0` | Адрес прослушивания. |
| `TZ` | `Asia/Shanghai` | Часовой пояс контейнера (имя IANA). Влияет на логи и локальное время, которое отдаёт бэкенд. Меняется в `docker-compose.yml` или `.env`. |
| `CONFIG_PATH` | `/app/config.xml` | Расположение `config.xml`. |
| `DATA_DIR` | `/app/data` | Артефакты + `state.json` + сгенерированные иконки PWA и manifest. |
| `PUBLIC_DIR` | `/app/public` | Собранное приложение SPA (вшито в образ). |

| `GITHUB_TOKEN` | *(пусто)* | Необязательный. Повышает лимит API. |

```bash
dig +short mirror.example.com
```

## Шаг 6 — обратный прокси nginx + TLS

### 1. Установите nginx и certbot

```bash
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
```

### 2. Создайте конфигурацию сайта

`/etc/nginx/sites-available/biangbiang`:

```nginx
# --- проверка ACME + редирект с HTTP на HTTPS -----------------------------
server {
    listen 80;
    listen [::]:80;
    server_name mirror.example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}
```

Включите её:

```bash
sudo ln -s /etc/nginx/sites-available/biangbiang /etc/nginx/sites-enabled/biangbiang
sudo mkdir -p /var/www/html
sudo nginx -t && sudo systemctl reload nginx
```

### 3. Получите сертификат

```bash
sudo certbot certonly --webroot -w /var/www/html \
  -d mirror.example.com \
  --agree-tos -m you@example.com --no-eff-email
```

certbot установит таймер systemd, так что продление будет автоматическим.


### 4. Добавьте блок сервера HTTPS

Теперь замените конфигурацию полной версией — она сохраняет блок ACME / редиректа выше и добавляет TLS с обратным прокси:

```nginx
# --- проверка ACME + редирект с HTTP на HTTPS -----------------------------
server {
    listen 80;
    listen [::]:80;
    server_name mirror.example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

# --- HTTPS ----------------------------------------------------------------
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name mirror.example.com;

    ssl_certificate     /etc/letsencrypt/live/mirror.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mirror.example.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options "nosniff" always;

    # Артефакты бывают на сотни МБ: передавайте потоком,
    # не буферизуйте их целиком в nginx.
    proxy_buffering off;
    proxy_request_buffering off;
    client_max_body_size 0;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;

        # Большие загрузки нельзя обрывать на полпути.
        proxy_connect_timeout 30s;
        proxy_send_timeout    3600s;
        proxy_read_timeout    3600s;
    }
}
```

Примените конфигурацию:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> **Почему только локальный интерфейс?** Файл Compose публикует `127.0.0.1:8080:8080`, поэтому контейнер недоступен напрямую из интернета — весь публичный трафик идёт через nginx, который и завершает TLS. Если nginx не нужен и вы хотите выставить порт напрямую, замените `ports:` на `"8080:8080"` — но тогда не будет HTTPS, и PWA перестанет устанавливаться.

### Альтернатива: nginx тоже в контейнере

Если хочется управлять всем через Compose, добавьте сервис nginx в ту же сеть, уберите маппинг `ports:` у сервиса `biangbiang`, замените `proxy_pass` на `http://biangbiang:8080;` и смонтируйте сертификаты вместе с `nginx.conf`. Вариант с nginx на хосте проще в обслуживании продления сертификатов, поэтому он и рекомендован.

## Шаг 7 — проверьте развёртывание

```bash
# 1. DNS указывает на ваш сервер
dig +short mirror.example.com

# 2. TLS работает, а HTTP перенаправляет
curl -sI http://mirror.example.com | head -1      # 301 -> https://
curl -sI https://mirror.example.com | head -1     # 200

# 3. API отвечает через прокси
curl -s https://mirror.example.com/api/health

# 4. Контейнер не выставлен на публичный интерфейс
ss -tlnp | grep 8080        # должно быть 127.0.0.1:8080, никогда 0.0.0.0:8080

# 5. Артефакт скачивается
curl -sI "https://mirror.example.com/dl/{owner}/{repo}/{version}/{file}" | head -1
```

Затем откройте `https://mirror.example.com` в браузере и проверьте:

- В шапке видны заголовок и favicon, заданные в `<title>`.
- Каждый `<project>` — одна карточка с меткой версии и кнопками скачивания для каждого артефакта.
- Кнопка «Открыть репозиторий» ведёт обратно на GitHub.
- Переключатель темы предлагает «Как в системе / Светлая / Тёмная».
- Если задано `<sortable>true</sortable>`, в шапке появляется список сортировки (По алфавиту / По обновлению / Больше файлов / Меньше файлов).
- Если задано `<lang>` (например, `<lang>ru_ru</lang>`), весь интерфейс — тексты, форматы дат и подписи Ant Design — переключается на этот язык. Без тега остаётся упрощённый китайский.
- Если задано `<accent>` (например, `<accent>volcano</accent>`), элементы, обычно синие — метки версий, ссылка «Открыть репозиторий», — принимают этот цвет. Без тега остаётся синий по умолчанию.
- Если задано `<font>` (например, `<font>assets/MyFont.woff2</font>`), весь текст на странице — включая кнопки, теги и списки Ant Design — использует этот шрифт. Без тега или при отсутствующем файле остаётся системный шрифт.
- Масштабирование двумя пальцами отключено, поэтому страницу нельзя приблизить целиком; прокрутка и сдвиги по горизонтали и вертикали работают как обычно. Масштаб из меню браузера или системных средств доступности по-прежнему доступен.

### Установка как PWA

Поскольку сайт теперь отдаётся по HTTPS, service worker может зарегистрироваться, и приложение можно установить:

- **iOS Safari:** «Поделиться» → *На экран «Домой»*.
- **Android Chrome:** меню → *Установить приложение*.
- **Chrome / Edge на компьютере:** значок установки справа в адресной строке.

Приложение по замыслу **не работает офлайн** — service worker это чистый сетевой проброс.

## Текущая эксплуатация

### Просмотр логов

```bash
docker compose logs -f --tail=100 biangbiang
```

### Ручной запуск синхронизации

Кнопка «Проверить обновления» на странице вызывает `POST /api/refresh`. Из командной строки тоже можно:

```bash
curl -X POST https://mirror.example.com/api/refresh
```

### Обновление biangbiang

Стабильные релизы публикуются как теги. Загрузите теги, переключитесь на самый свежий и пересоберите контейнер:

```bash
cd /srv/biangbiang
git fetch --tags
git checkout "$(git tag --sort=-v:refname | head -1)"   # самый свежий тег релиза
docker compose up -d --build
```

> Переключение на тег оставляет вас в состоянии detached HEAD, что для развёртывания не имеет значения. Чтобы закрепить конкретную версию, замените `"$(...)"` на имя тега, например `v1.0.2`.

В версии для разработки (ветка `main`) по-прежнему нужен `git pull`:

```bash
cd /srv/biangbiang
git pull
docker compose up -d --build
```

`./config.xml`, `./assets` и `./data` лежат на хосте, поэтому обновления их не затрагивают.

### Резервные копии

По-настоящему незаменимы только конфигурация и зеркалированные файлы:

```bash
tar czf biangbiang-$(date +%F).tar.gz config.xml assets data
```

Файл `data/state.json` позволяет сайту отрисоваться сразу после восстановления, не дожидаясь первого цикла опроса GitHub.

### Владелец файлов

Контейнер работает от uid/gid **1000** (`node`). Смонтированный через bind mount каталог `./data` сохраняет владельца с хоста — а если он создан через `sudo`, это `root` — и непривилегированный процесс писать туда не может.

Это делает за вас entrypoint: когда контейнер стартует от root, он сначала меняет владельца `DATA_DIR` на `node`, а затем сбрасывает права. Поэтому конфигурация Compose по умолчанию не требует ручного `chown`.

Если контейнер вообще не стартует от root, entrypoint бессилен. Когда вы задали `user:` в Compose или запускаете `docker run --user`, `./data` уже должен быть доступен на запись этому uid:

```bash
sudo chown -R 1000:1000 /srv/biangbiang/data
```

### Лимиты API GitHub

Неавторизованные запросы ограничены **60 в час** (на IP-адрес). Для нескольких проектов и одной проверки в сутки этого с запасом хватает. Если проектов много, создайте [токен с узкими правами](https://github.com/settings/tokens?type=beta) (доступ только на чтение публичных репозиториев), впишите его в `.env` как `GITHUB_TOKEN` и перезапустите:

```bash
docker compose up -d --force-recreate
```

### Изменение интервала проверки

Задайте `CHECK_INTERVAL_HOURS` в разделе `environment:` файла Compose (минимум `0.05`, то есть 3 минуты) и пересоберите контейнер.

## Диагностика

| Симптом | Причина / решение |
|---|---|
| Возвращается `503 Frontend build not found.` | В `PUBLIC_DIR` нет `index.html`. Не переопределяйте `PUBLIC_DIR` — SPA вшита в образ по пути `/app/public`. |
| Все карточки показывают «Ошибка синхронизации» с `404 Not Found` | `<repo>` не существует или записан с ошибкой; а если репозиторий приватный — у токена недостаточно прав. |
| В логе `overwrite.xml not found at /app/overwrite.xml` | Проект использует `overwrite@{number}`, но файла нет. Создайте `./overwrite.xml` — см. [Монтирование overwrite.xml](#монтирование-overwritexml). |
| Карточка показывает `overwrite.xml has no <overwrite> block with <id>N</id>` | Для числа из `overwrite@N` нет соответствующего `<id>N</id>` в `overwrite.xml`. Сверьте оба файла или добавьте недостающий блок. |
| `overwrite.xml` сообщает `EISDIR` / «is a directory» | Монтирование включили, когда файла ещё не было, и Docker создал каталог. Выполните `rmdir ./overwrite.xml`, создайте файл с тем же именем и пересоберите контейнер. |
| Кнопка скачивания ручной записи отдаёт 404 | Ссылка в `<file>` неверна или устарела — кнопка ведёт прямо по этому адресу, biangbiang её не проверяет. |
| Сообщение `API rate limit exceeded` | Задайте `GITHUB_TOKEN` в `.env`. |
| Карточка не показывает иконку | Неверный путь в `<icon>` или файл недоступен для чтения uid 1000. Пути разрешаются относительно `config.xml`. |
| Иконки PWA остались стандартными | Отсутствует или нечитаем `<favicon>`, либо ImageMagick завершился с ошибкой. Посмотрите `docker compose logs \| grep '\[pwa\]'`, затем выполните `docker compose restart biangbiang`. |
| Имя установленного приложения осталось стандартным | `manifest.webmanifest` создаётся из `<title>` при старте. Убедитесь, что `<title>` в `config.xml` верен, и выполните `docker compose restart biangbiang`. Запись `[pwa] cannot read` в логе означает, что в сборке фронтенда нет шаблона manifest. |
| `./data` сообщает `EACCES` / `permission denied` | Контейнер не может писать в каталог данных. Если он стартует от root, entrypoint сам исправляет владельца — значит, вы задали `user:` / `--user` или смонтировали `./data` только для чтения. Выполните `sudo chown -R 1000:1000 ./data`, а если добавили `:ro`, уберите его. |
| `http://127.0.0.1:8080` работает, а домен — нет | Проверьте `proxy_pass` и `server_name` в nginx, а также пропускает ли брандмауэр порты 80/443. |
| Скачивание обрывается на полпути | Увеличьте `proxy_read_timeout` / `proxy_send_timeout` в конфигурации nginx. |
| Service worker не регистрируется | Сайт должен открываться по **HTTPS** (или с `localhost`). Прямой доступ по IP через обычный HTTP — это не безопасный контекст. |
| Проверка certbot не проходит | DNS ещё не разошёлся, порт 80 занят или заблокирован, либо другой блок сервера перехватывает тот же `server_name`. |
| Диск заполняется старыми файлами | Каждый проект хранит только последнюю версию. Проверьте, нет ли в `./data` других данных, и подумайте об изменении `DOWNLOAD_CONCURRENCY` или увеличении диска. |
